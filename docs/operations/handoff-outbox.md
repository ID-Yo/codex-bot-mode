# Handoff outbox (#399)

The handoff outbox lets an agent report to its project Manager and end its turn at once, without waiting for the Manager and without spending model tokens on polling. A local script queues the report on disk; a small local pump (no model calls) delivers the queued reports to the Manager thread one at a time.

Source files: `scripts/team_room/outbox.py` (queue, pump and CLI) and `scripts/team_room/requests.py` (queues a report when a request is closed). This text describes source behaviour. It is not evidence that any project has the outbox installed or running.

## Flow

1. `requests.py reply` or `requests.py verdict` closes the request in the ledger first. After that it queues one short report (request id, who closed it, outcome, task summary, evidence link, next owner) with `.bot-mode/outbox.py send` and starts a background pump.
2. The queue is a SQLite file, `.bot-mode/outbox/queue.sqlite`, with the rows in arrival order.
3. The pump reads the Manager thread through the local Desktop Relay. It sends the next report only when the thread is idle (a chat that Desktop has not loaded, status `notLoaded`, counts as idle when its newest turn is not in progress), then waits until that message shows up as a new Manager turn (a new turn id, or the thread reported active) and until that turn has finished, before it considers the next report. Reports from several agents therefore arrive as separate Manager turns and never as steers inside a running turn.
4. Anything the pump cannot prove is treated as not safe to send: an unknown thread status, a read error (it backs off), or no new Manager turn within `--turn-timeout` seconds (default 120). In the last case the report counts as delivered, the pump stops with exit code 4 and leaves the remaining rows pending; run the pump again after looking at the Manager thread.

The target is always the project Manager, resolved from `roster.json` (or `roster.py links`) when the pump needs it, so a replaced Manager chat is picked up at the next delivery. A report is not routed to the requester of the request: the ledger row and its reply link stay the record for any other requester, and the Manager is the single reader of the queue.

## A closed request is never reopened by the outbox

If queueing fails after the ledger was closed (the outbox command exits non-zero, times out or cannot start), `reply` and `verdict` still print the closed request and exit 0. They write a warning to stderr that starts with `warning: request <id> is closed` and contains the exact `outbox.py send` command to queue the report by hand. Do not repeat the closeout (for `verdict` that would post a second comment). A repeated `reply` with the same outcome is harmless: it keeps the ledger row and queues the report again under the same dedupe key. A project without `.bot-mode/outbox.py` queues nothing; `reply` and `verdict` then print `warning: request <id> is closed, but this project has no .bot-mode/outbox.py` (the closed request is never reopened). A task that was assigned without a ledger entry never reaches `reply`; the agent queues its report with `outbox.py send --to <requester or manager> --by <bot> --text ...` (shared BASE, 'Reporting back and delivery').

## States and rules

| State | Meaning |
|---|---|
| `pending` | Waiting for its turn. |
| `sending` | The pump has called the relay and has no answer yet. Opening the queue from `send` or `list` never changes it. |
| `delivered` | The relay accepted the message. |
| `failed` | Terminal: the target thread could not be resolved. |
| `ambiguous` | The outcome of the send is unknown (error or timeout after the relay was called, or the pump stopped while sending). Being reconciled; holds later rows for the same recipient. |
| `needs-attention` | An ambiguous row that stayed unresolved for the attention time (default 30 min). Shown by `status` and `list`; holds nothing. |
| `skipped` | An operator decided never to send it. |

**Ambiguous delivery is reconciled automatically (#422).** Every delivery begins with a stable `[Outbox delivery: <id>]` marker. The pump reads the actual destination thread (one history read per thread, up to 5 pages of 50 turns) at its start, after every failed send and every 30 s while rows are unresolved, and decides from evidence only:

- A user message with the marker proves delivery: the row becomes `delivered` (also a `needs-attention` row, later). Only messages that start with an outbox marker or digest header count; a marker quoted in another message or echoed by an agent is not proof.
- No marker proves non-delivery only when the read was **complete, well formed and unredacted**, the row is still `ambiguous` and the retry grace (default 10 min since it became ambiguous) has passed. Complete: every reply has `turns` and `items` as lists and `page` as a mapping, and the last page names no further cursor within the bound of 5 pages. Unredacted: at least one user message came back with more than one character of text, because the relay reduces a chat that is only read-only reachable to one character per item and no marker can be found in that (the relay's read policy is not changed). Then the row goes back to `pending` at its place and is sent again (note `auto-retry` on the row). A malformed, cut-off, redacted, bounded, empty or unreadable history proves nothing: the row stays `ambiguous` (later `needs-attention`) and is not resent; a marker found on the pages that were read still proves delivery. A grace of 0 turns automatic retry off.
- **Unresolved rows are looked at again.** A pump that has nothing else to deliver rereads the history of unresolved rows every 30 s, 3 times (`rechecks` in `outbox-config.json`), then ends; a late marker still turns the row into delivered without any new report. `outbox.py status --heal` starts such a pump for a queue that holds only ambiguous or needs-attention rows (the watchdog runs it every 5 minutes). Rows older than the TTL (12 h) are left to the operator, so a row that never resolves does not cause rereads for ever; `status` shows the count of rows still worth a reread as `recheckable`.
- Residual risk, stated plainly: if the relay accepts a stale send much later than the grace period (for example after a long stall), the Manager may see a report twice. A duplicate report is the price of never losing one; every report carries its marker and id.

**An unresolved row holds only its own recipient.** While a row is ambiguous, later pending rows for the same recipient (same target name or same thread) wait, so the order is kept and a late arrival cannot overtake. Rows for other recipients are delivered as usual; nothing holds the whole project.

**Needs attention.** A row still ambiguous after the attention time (default 30 min, `--attention-minutes` or `attention_minutes` in `outbox-config.json`) becomes `needs-attention`: `outbox.py status` counts it and reports a problem, `outbox.py list --state needs-attention` shows it, and it no longer holds later rows. It is never resent without proof. `status` applies this change itself, so it also happens when no pump runs. An operator decides:

```text
python -B .bot-mode/outbox.py --project <project> resolve <id> --as delivered   # the report arrived
python -B .bot-mode/outbox.py --project <project> resolve <id> --as skipped     # never send it
python -B .bot-mode/outbox.py --project <project> resolve <id> --as retry       # it did not arrive: send it again, in its place
```

`resolve` accepts an ambiguous or needs-attention row (and `retry` also a failed one), takes `--note` for a reason, and starts the pump again when rows are pending.

**A chat without an active turn id is not an ambiguous send (#426).** Desktop answers a steer into a chat it believes is running, but that has no turn id, with HTTP 503 and the text `Cannot steer conversation <id> without an active turn id`. Only an error that is exactly this refusal is treated as a refusal before anything started (the whole text must match "HTTP Error 503: <reason> (Cannot steer conversation <id> without an active turn id)", nothing before or after, and never a text with "outcome unconfirmed" or "do not resend", whose stderr tail can quote the same line): the rows go back to `pending` in their place (note `not sent: ...`), only this recipient is set aside with a growing pause (poll interval times 2, 4, 8 ... up to 30 s, reset after a delivery), and rows for other recipients are delivered as usual. Every other 503, including an unconfirmed outcome, stays `ambiguous` and is reconciled as above.

Risks, stated plainly: it is not proven that Desktop never takes a message when it gives this refusal (the Desktop code is not in this repository), so a report may be delivered twice. The second delivery repeats the same `[Outbox delivery: <id>]` marker line, so the Manager can recognise it. A real turn-state race cannot be reproduced without a live Desktop; the tests use a fake relay.

**Digest.** When several rows wait for the same recipient (typically because it was busy), the pump sends them as one message in creation order: a header `[Outbox digest: N reports, oldest first]`, then per report its marker line, `From: <sender> (<time>)` and the text. It is one Manager turn, so the pump waits for one turn marker, and each row keeps its own state (all `sending`, then all `delivered`, or all `ambiguous` together; each row is confirmed on its own by its marker). A digest never mixes recipients, never passes an earlier ambiguous row of its recipient, and stops at 20 reports or about 24000 characters (**--digest-max**, `digest_max`; 1 sends rows one by one). A single row is sent exactly as before.

**Failed and ambiguous rows keep their dedupe key.** The key is `request:<id>:<by>:<outcome>`, so the same report is not queued twice, also when two senders race (the second one gets the existing row). A failed or ambiguous row is re-queued only by `resolve --as retry`; the row keeps its original place in the order, so reports queued after a failed row may already have been sent by then. Fix the cause first (for example the Manager binding in the roster).

**One pump per project.** The pump holds an operating system lock on `.bot-mode/outbox/pump.lock`. The system releases it when the pump ends or dies, so there is no stale lock to take over and no process id to reuse. A second pump exits at once with code 0. A row left `sending` by a dead pump (every row of a digest) is turned into `ambiguous` by the next pump and then reconciled as above.

**Loopback relay only.** The relay descriptor (`relay.json`) is used only when its URL is plain `http` to `127.0.0.1`, `localhost` or `::1` without credentials, query or fragment. Any other descriptor is ignored with a message that never prints the token, and the client does not follow redirects, so the relay token is not sent to another host.

**Retry and skip from Office (#424, S4-E).** The Delivery panel can decide an `ambiguous` or `needs-attention` row. Office does not touch the queue and sends nothing to Desktop: the endpoints `GET /api/outbox-rows?project=<name>` and `POST /api/outbox-resolve` (`{project, id, action: retry|skip, confirm: true}`) run the project's own installed `outbox.py list --state` and `outbox.py resolve <id> --as retry|skipped --note "office panel"` without a shell and with a 30 s limit. Both need the Office token and the same origin. The project is named by the caller but found only in the supervisor's fresh `supervisor-status.json`; an unknown name, a missing or old status, a name listed twice, a missing outbox.py or an outbox.py too old to know `list --state` or `resolve` is a refusal. Any other row state or an unknown id is 409, a timeout or an unclear answer is 503 (outcome unknown, never success). The list shows id, state, sender, target and age, never the report text, the error or a path. Retry starts the project's pump through the existing `resolve` (that is how the row is delivered), so the Manager may see the same report twice with the same marker line. Every attempt, also a refused one, is appended to `.bot-mode/delivery-actions.jsonl` of the Office checkout (time, project name, id, action, state seen, result, reason, `by: office-owner`), without text or paths. The journal tells an unknown outcome (a timeout or an unclear answer of resolve, `outcome: unknown`) from a refusal that changed nothing (`outcome: none`).

The Delivery panel shows these rows under their project with Retry and Skip. Each button first opens an inline confirmation: Retry warns that the report may already have arrived, that the Manager may see it twice and that the row may wait behind other unconfirmed reports for the same recipient, Skip says the report is never sent. Only the confirmation sends the one POST. The panel shows what the server answered: `state` `pending` or `skipped` is shown as done, a 400, 404 or 409 as the server's reason, and a 503, a lost connection or any other answer as `Unknown outcome` (never as success). The list is read again after every decision. It shows at most the newest 20 rows per state, and the panel says so when the list is cut: older rows cannot be decided from Office.

## Install and limits

- A new project launch (`install-team`, Director or agent install) installs `.bot-mode/outbox.py` and, when missing, `.bot-mode/outbox-config.json` (`relay_root` of the CBM checkout) next to `roster.py` and `requests.py`, and records all of them as tool components in the installation inventory (#415). Existing projects receive the files and the updated BASE through the guarded release procedure after Review and QA; the watchdog reports a registered project that has `requests.py` but no `outbox.py`.
- Not verified here: a live relay, the real Manager thread, and an installed project. The tests use a fake relay that registers and finishes turns after a number of reads.
- The Agent Monitor outbox that forwards Monitor reports is a different mechanism (`docs/operations/agent-monitor.md`).


## Reliability (#401)

The Desktop relay is a critical component: without it nothing is delivered. Since #421 it does not need the Manager chat: the standalone relay finds the Desktop tool pipe by name and takes the Manager from the roster, so the supervisor task can restart it. Registering it from the Manager chat remains a fallback. The design is detect-early, heal where possible and never fail silently.

**Recipients.** The relay sends a report only to a chat that is appointed: the relay project's own roster, the registry Manager of each registered project, and every other chat bound in a registered project's roster (a Director, a sub-Manager, a worker; #417). A thread that is bound nowhere is refused with HTTP 400 and its row is quarantined as ambiguous. Waiting on a chat and reading its content keep the stricter rules (appointed chats only; other bound chats are readable as thread status and turn metadata).

- **Pump waits.** While the relay is down the pump keeps running, re-reads the relay descriptor with a capped backoff (a restarted relay has a new port and token) and writes `.bot-mode/outbox/pump.heartbeat.json`.
- **TTL.** A pending row older than 12 h becomes `expired` (`outbox.py list --state expired`).
- **Retention (#422).** `outbox.py prune [--keep N] [--max-backups M] [--ttl-hours H] [--dry-run]` expires old pending rows (the TTL above) and deletes all but the newest N delivered rows (default 200), and the same for skipped and expired rows. Pending, sending, ambiguous, needs-attention and failed rows are never deleted. Whenever anything would change, the database is first copied with the SQLite backup API to `.bot-mode/outbox/backups/queue-<time>.sqlite`; only the newest M copies (default 5) are kept. A deleted row frees its dedupe key, so an old report could be queued again. A pump that finds more than twice N delivered rows at its start prunes by itself, so the file stays bounded without a person. `--dry-run` prints the counts and changes nothing.
- **Settings.** `.bot-mode/outbox-config.json` may hold `attention_minutes`, `retry_grace_minutes`, `digest_max`, `keep_rows` and `max_backups` next to `relay_root`; a command line option wins, then the file, then the default. The `send`, `list`, `status`, `pump` and `resolve` commands keep their arguments and output; `needs_attention` is a new field of the `status` JSON.
- **Status.** `outbox.py status [--heal]` prints JSON and exits 5 when work waits without a reachable relay or a running pump, or when an ambiguous or needs-attention row needs a look. `--heal` starts a missing pump, including to reconcile ambiguous rows.
- **Send is loud (#424).** After the receipt line (`Queued outbox handoff <id> for <target>. Turn complete.`, unchanged: `doctor` reads it) `send` prints `Queue: <n> pending, oldest <s> s.` and `Relay: up|DOWN. Pump: running|started now. Last delivery: <age> ago|none recorded.`. When the relay is down it says on stderr that the report is NOT delivered yet but stays queued, and names the fallbacks: write the result directly in the Manager thread with the thread tool, keep the closed request in the ledger (`requests.py reply`), comment on the linked issue. The same warning appears when the oldest row has waited more than 10 minutes although the relay is up. `status` has a new field `last_delivered_at` (null when nothing was delivered yet). The exit code of `send` and the receipt are unchanged.
- **Supervisor.** `scripts/relay_watchdog.py --all-projects --restart [--notify]` probes the relay, restarts it without the Manager chat when it is down or serves a replaced Manager chat, runs `status --heal` per project (a pump that holds its lock without a heartbeat for 180 s is ended and replaced, but only when the process is proven to be this project's pump; an unprovable one is reported and left alone), compares installed `outbox.py`/`requests.py` with the repo and writes `.bot-mode/relay-health.json`. The task `Codex Bot Mode Supervisor` (`scripts/supervisor_task.ps1`) runs it without a model every 2 minutes and at logon, hidden, also on battery. While Codex Desktop is closed nothing can be delivered; that is reported as waiting, and as a problem only when reports are waiting. Codex Office is optional: its state is in the report, and it raises an alarm only when the task was installed with `-RestartOffice`. A relay that still serves a replaced Manager chat is never reported healthy.

**Supervisor status file (#424).** Every pass also writes `.bot-mode/supervisor-status.json` (schema 1, next to the health file, written atomically; `--status-file` overrides). It holds the pass time `at`, `pass_seconds`, the expected `interval_seconds` (the task passes `--interval-seconds`; default 120), the supervisor `pid` and `version`, `desktop_running`, `office_ok`, `relay` {`ok`, `manager_changed`, `last_restart` {`at`, `reason` (`relay down` or `Manager chat replaced`), `ok`, `detail`}}, `last_pump_action` (a stuck pump replaced or not stopped, or a pump started), one entry per project (pending, oldest_pending_seconds, ambiguous, needs_attention, relay_reachable, pump_alive, last_delivered_at, problems) `problems` and `incidents_error` (null, or the failure of the incident bookkeeping). The last restart and the last pump action are kept from pass to pass until a newer one replaces them. `relay-health.json` is unchanged. A reader uses `scripts/team_room/supervisor_status.py`: `read()` returns state `ok`, `problems` or `unknown`. A missing, unreadable, foreign-schema, future-dated or old file (older than three intervals) is **unknown**, never healthy, because a supervisor that stopped cannot report its own death. `supervisor_task.ps1 -Status` prints the file.

**One alert per incident (#424).** The supervisor no longer announces a fault every time it comes back. Each problem gets a stable key without numbers (`relay-down`, `relay-wrong-manager`, `office-down`, `desktop-closed`, and per project `needs-attention:<project>`, `pump-down:<project>`, `pump-stuck:<project>`, `outbox-missing:<project>`, `outbox-drift:<project>`, `ambiguous:<project>`, `pending-stale:<project>`, `check-failed:<project>`, `status-failed:<project>`; the project is the registered project's name or, for a project that has no outbox and so is not registered with the supervisor, the name in front of the problem text; an unknown problem becomes `other:<words>`). Open incidents are kept in `.bot-mode/local/incidents.json` (local, not shared) and listed as `incidents` in `relay-health.json` for Office; `.bot-mode/local/incidents.jsonl` gets one line per event (opened, returned, owner_message, closed with how long it lasted, row_skipped). An incident opens once and then: **one row to the project's Manager** through the outbox (sender `supervisor`, dedupe key `incident:<key>:<opened>:<n>`; a fault of a project goes to that project's outbox, a machine fault such as the relay to this repository's outbox; no row where no outbox is installed or where the roster names no Manager, logged once as row_skipped; a missing Manager is tried again every pass, a missing outbox is final), a reminder row after 6 h while it is still open, and for a fault that needs the owner (severity `owner`: the relay is down and the supervisor could not restart it, or it serves a replaced Manager chat) **one Windows message** (`msg`, only with `--notify`) after 10 minutes, so a fault that heals itself never pops up. Severity `manager` sends the row only, severity `info` (`ambiguous`, `pending-stale`, `desktop-closed`) is recorded and shown but never sent. A fault that disappears closes only after 15 minutes without it and at least 3 clean passes (a long gap between two passes is not proof); a return inside that time is the same incident (a flapping fault is one alert, not one per flap), a return later is a new incident with a new row. A row that could not be queued is tried again in the next pass. A damaged record in incidents.json (a missing or mistyped field) is dropped when the file is read and logged as state_repaired; its problem opens again as a new incident, and the rest of the file is kept. Any failure of this bookkeeping is recorded as incidents_error in relay-health.json and in the status file and never stops the pass.

**Office delivery panel (#424).** The Office dashboard shows a "Delivery" section in its right column (`scripts/team_room/static/delivery.js`). It reads `GET /api/outbox-health` (same-origin and Office token required, like the owner inbox), which `scripts/team_room/outbox_health.py` builds from `.bot-mode/supervisor-status.json` of the checkout that runs Office, plus the open `incidents` of `relay-health.json` while that file is as fresh as the status file. Office makes no Desktop or relay call for it and dispatches nothing (the status itself is read-only; the only write is the confirmed Retry or Skip decision described above). The panel shows the state (Healthy, Problems or Unknown with the reason and how long ago the supervisor reported), the relay with the last restart reason, the last pump action, the problem list, open incidents with their remedy, the supervisor's `incidents_error` when its incident bookkeeping failed in the last pass, and per project: waiting reports and the oldest age, last delivery, pump running or stopped, and the counts that need attention or are unconfirmed. A missing, unreadable or stale status file is Unknown and shows no numbers: unknown is neither healthy nor zero. The model carries no project paths (problem, incident and error texts are shown as the supervisor wrote them, up to 300 characters). Limit: Office looks for the status file in its own checkout (`project.ROOT`); an Office started from another copy than the one the supervisor task runs from shows Unknown until both use the same checkout. Retry and Skip for reports that wait for a decision are described in the paragraphs above (S4-E).

**The ledger is the truth, the outbox only wakes (#425).** A report in the outbox is a wake-up call; the request ledger (`.bot-mode/local/requests.json`) records what was asked and what was answered. Whoever acts for the Manager runs `requests.py pending [--for manager]` at the start of every turn and on every heartbeat. It reads, without model tokens and without changing anything: the open ledger requests addressed to the bot (age, due or OVERDUE, link, summary), how many open requests the bot waits on and which of them are overdue, the requests the bot sent that were answered in the last 24 hours (`state: answered` in the ledger: recipient, outcome, age, reply link, summary; this is how a closeout made with `requests.py reply` is found without the relay) and the ones answered `partial` that the requester has not accepted yet, at any age, and the outbox rows for the bot that are not delivered yet (pending, sending, ambiguous, needs-attention, failed) with sender, state, age and the first 200 characters of the text, at most 10 rows. Expired rows are only counted. A missing outbox is said so; an unreadable ledger or outbox is printed as `UNKNOWN`, never as empty. It prints `Nothing waiting for <bot>.` only when the ledger and the outbox were both read and are empty (a project without a queue file has no outbox rows). When a source is UNKNOWN the last line is `Cannot tell what waits for <bot>: <source> is UNKNOWN; look by hand.`, whatever the other source shows. It reads only the ledger and the outbox: a comment on the linked issue is not found by it, so open the issue of an answer (its link is in the entry). The exit code is always 0. A pending row is delivered by the pump; an ambiguous or needs-attention row is decided with `outbox.py resolve <id> --as delivered|skipped|retry`.

**Agent fallback when the relay is down (#425).** `send` queues the report and says so (see "Send is loud"). The agent then makes sure the Manager still gets the result, in this order: (1) write it directly in the Manager thread with the thread tool; (2) keep the closeout in the ledger with `requests.py reply` (the ledger keeps it even when no outbox report can be queued, and the command says to report by hand); (3) comment on the linked issue. `requests.py pending` then shows the Manager the answered request with its reply link (and the undelivered row, if the project has an outbox), so the result does not depend on the relay coming back; the issue comment is read by opening the linked issue.

**Chaos suite (#426).** `tests/test_outbox_chaos_426.py` runs the real `outbox.py` (pump and send, each in its own process) against a scripted stand-in for Desktop and its relay (`tests/outbox_chaos.py`): a real HTTP server on 127.0.0.1 that answers like the relay (`POST /call`, the `X-Office-Relay` token, 403 for a wrong token, 503 when Desktop fails a call) in front of a few in-memory chats. It never touches a live relay, queue or task. It covers: the relay dying after it took a message and before it took it (the row becomes ambiguous, is confirmed from the chat history and never sent twice, or is sent once when the history proves it missing); a pump killed mid-send, before and after the relay took the message; the pump lock being free after a kill and held by a live pump; a restarted relay with a new port and token (the pump reads the new descriptor, the old token is refused); Desktop restarting (reads fail, then a chat that is not loaded and shows no turns: nothing is sent until the chat is readable); a chat that is not loaded but readable; three agents reporting at once with a repeated dedupe key; a busy Manager that does not hold another recipient; an unconfirmed row that holds only its own recipient. A recipient whose chat the relay cannot read (the relay answers 503, for example thread not found) is set aside by the pump with a growing pause (at most 30 s) and its row stays pending, so reports for the other recipients are not held behind it; a refused token (401 or 403) or an unreachable relay still makes the pump read the relay descriptor again. Recovery after a relay restart can need a new pump: a pump that cannot reconcile gives up after a few rereads and the supervisor's `status --heal` starts the next one, which is what the suite does too. What it cannot show without a live Desktop: that Desktop accepts `send_message_to_thread` for a live chat and starts a Manager turn, the real named pipe between relay and Desktop and what a pipe rename or a Desktop restart does to loaded chats, the real timing of a busy Manager, and the Windows message popup. Those stay with `doctor.py --canary` (opt-in, wakes the Manager) and a manual check.

**Canary (#426).** `outbox.py canary [--to manager] [--every-minutes 10] [--limit-minutes 5]` is a zero-token probe of the whole delivery path. It queues a canary when none is pending and the newest is older than `--every-minutes`, starts a pump for it if none runs, and prints JSON: `queued`, `pending_seconds`, `last_ok_at`, `last_latency_seconds` (queued to processed), `last_read_seconds` (the relay round trip), `last_chat_status`, `last_error` and `problems`; exit 5 when a canary has waited longer than `--limit-minutes` without being processed. The canary is a record in its own table (`canary` in `queue.sqlite`, the newest 20 kept), never an outbox row: it is in no digest, no count of `status`, no `list` and no `requests.py pending`. The pump processes it as soon as it has a relay client, also while the Manager is busy: it resolves the Manager chat from the roster, reads its status with the same read-only call it uses before every delivery and records the times. Nothing is sent, so no model turn runs. An answer the pump would not deliver into is not a success: no text status, a status other than active, idle or notLoaded (for example `systemError`), or notLoaded with unreadable turns or a newest turn of unknown status. The canary then stays pending with the status in `last_error`, is tried again, and becomes the problem after the limit. Two callers at the same moment queue one canary. It proves that the queue file, the pump, the relay descriptor and token, the roster and Desktop's answer work, with a measured latency. It does not prove that Desktop accepts a message and starts a turn (`doctor.py --canary` does, and wakes the Manager). A report that waits behind a busy Manager is not a canary problem; the age of the oldest pending report in `status` shows that. `status` carries the same facts as an extra `canary` object (information only) and `status --heal` starts a pump for a waiting canary.

**Canary in the supervisor pass (#426).** Every pass also runs `outbox.py canary` in each checked project (`--canary-every-minutes`, default 10, 0 switches it off; `--canary-limit-minutes`, default 5). A project whose installed `outbox.py` has no canary command yet is Unknown (null in the status file), not a problem; the drift check names the old copy. A canary that waited longer than the limit becomes the problem `<project>: outbox canary has waited ...`, which the incident classifier maps to the key `outbox-canary:<project>` with Manager severity: one row to the Manager per incident, no Windows message, so no repeating windows. While the relay is down the canary adds nothing, because that is the incident `relay-down`. The per-project entry of `supervisor-status.json` carries `canary`: `last_ok_at`, `last_latency_seconds`, `last_read_seconds`, `last_chat_status`, `pending_seconds` (null when unknown). The Office Delivery panel shows it per project as a small tag: `Canary <latency> s, <age> ago`, `Canary waiting <age>` or `Canary unknown` (never a good result without a canary: the latency is shown only when the chat status was active, idle or notLoaded and the time of the last success is valid; otherwise `Canary unknown`).

**Office registration and the Manager route (#454).** The relay serves the chats of the Office's own project and the chats appointed or bound in the roster of a project in the Office registry (`.bot-mode/local/office-project-roots.json` of the Office checkout). For a project that is not registered the relay refuses the read of its Manager chat with HTTP 400, the pump sets that recipient aside and the report waits without any other sign. `doctor.py` now has two read-only checks per project. `<project>: Office registration` is OK when the project root is in the registry, and a warning with the owner remedy when it is not, when there is no registry file, or when the file cannot be read (then it says that it does not know). `<project>: Manager route` makes one `read_thread` of the project's Manager chat (`turnLimit` 1, no outputs) through the project's relay descriptor, which is the read the pump makes before every delivery. It sends nothing, wakes nobody and does not run the project's `outbox.py`. HTTP 400 is a failure. When the relay answers with the text `Unappointed Desktop recipient refused` the check names the cause (the project is not in the registry or the chat is not bound in its roster). Any other HTTP 400 (the fixed `Invalid Desktop relay request`, which is all a relay answers until it has been restarted with the change described below, or an unrelated invalid request) gives "probably" and does not state a certain cause. A relay that is down, a timeout, a 401, 403 or 5xx are warnings that say unknown, and the check is skipped when there is no Manager chat or no reachable relay (the checks above report that). The doctor, `--fix`, `outbox.py`, the supervisor and the install never write the registry: registering a project is the owner's explicit step (the project onboarding in the Office panel, which the owner confirms) and the doctor reports it as not done until then. The doctor reads the registry of the checkout named by `--office-root`; a relay started with `CODEX_OFFICE_REGISTRY` pointing elsewhere can differ, and the Manager route check is the one that shows what the relay does. Known limitation: the supervisor and the watchdog walk the registry, so a project that is not registered is not watched by them (no incident, no health entry, no canary) until it is registered.

**Route refusal is named, recorded and shown (#454).** The relay of this repository answers a chat that is not appointed or bound in a registered project's roster with HTTP 400 and the text `Unappointed Desktop recipient refused` (before, every refusal and every malformed request got the same `Invalid Desktop relay request`, which stays the answer for every other invalid request). The change takes effect when the relay is restarted. `outbox.py` tells the two answers apart on the read it makes before each delivery (and on the canary read): the named text is a refusal of the chat, any other HTTP 400, which is also what a relay started before the change answers, is reported with "probably" because the cause cannot be known. Other failures (503, 401, 403, a relay that is down) are not route refusals and keep their handling. The pump writes the refusal into `.bot-mode/outbox/route-status.json` (`recipients` with `cause` named or probable, `first_at`, `last_at` and `count`), sets that recipient aside as before (the row stays pending, other recipients are delivered), and deletes the entry at the next read of that recipient's chat that the relay answers. `outbox.py status` lists the entries as `route_refused` and adds a problem that names the cause, says that registering the project in Office needs the owner's consent (the project onboarding in the Office panel) and that no tool writes the registry. `send` prints the same as a warning on stderr when the recipient has an entry; the receipt and the `Queue:` and `Relay:` lines on stdout are unchanged. For a registered project the supervisor shows the problem like any other outbox problem (an `other:` incident, one row to the Manager); for a project that is not registered the supervisor does not look at all (see the limitation above). The record is information: a failure to write it never stops a delivery. `tests/test_route_status_454.py` runs the real relay handler through the real client and the chaos relay with refused reads.
